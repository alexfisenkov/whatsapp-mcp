# Архитектура WhatsApp MCP

Статус: согласованное направление и локально реализованный core, 2026-10-06.
Adapters: WAHA Core NOWEB REST для personal linked-device; Meta Graph API для
Business. Локальные test results не доказывают connected server, реальный QR,
production webhook, доставку или deployed release.

## Контуры и runtime

Репозиторий содержит собственный TypeScript MCP server с transport entrypoints:
`dist/server.js` (stdio) и `dist/http-server.js` (Streamable HTTP + точные HTTP
routes). Node target `>=22 <23`; приложение не публикует port наружу само и
привязывается по умолчанию к `127.0.0.1`.

Каждый instance обслуживает ровно один adapter и account. На учебном сервере
infra подготавливает personal MCP (8857), Business MCP (8858), private WAHA Core
NOWEB container (8859), HTTPS reverse proxy, managed service identity и release
updater. Личные WAHA sessions изолированы в собственном volume; Business Graph
token и Meta App Secret принадлежат другому instance. Public repository содержит
код и install инструкции, но не session state/credentials владельца.

```text
Authenticated MCP client
      │ HTTPS gateway / one selected profile
      ▼
personal instance (127.0.0.1:8857)   business instance (127.0.0.1:8858)
typed registry + shared safe core       typed registry + shared safe core
WAHA REST + manual bounded sync         Graph REST + verified Meta callback
private SQLite history/audit             separate private SQLite history/audit
      │                                      │
private WAHA (127.0.0.1:8859)       public exact webhook → raw callback path
```

Публичные proxy paths определены в [`deployment/README.md`](../deployment/README.md).
WAHA engine API, dashboard, session storage и database не проксируются наружу.

## Capability registry

Provider definitions — источник MCP `tools/list`. Каждый инструмент имеет ID,
typed Zod schema, adapter, `read`/`guarded-mutation` kind и конечный upstream
handler. `docs/Матрица-возможностей.json` генерируется из definitions и показывает
default и явно условные инструменты. В runtime tools без backing implementation
не появляются; неизвестная capability даёт `UNSUPPORTED` до upstream request.

Registry не предоставляет generic `execute URL`, shell, SQL, произвольный
function name, code или path dispatch. Media operations принимают только
instance-local `mediaId`; операции со скрытым admin flag отсутствуют из default
tools/list.

### Personal linked-device

WAHA адаптер использует закреплённые NOWEB REST routes. Текущий набор включает
health/version/session status/account identity, bounded chats/messages/contacts/
groups/channels, message send/media/poll/reaction/read receipt, inbound media
download и ручную bounded history sync/search/context. Inbound download получает
чат/сообщение по ID, просит WAHA сохранить media, затем запрашивает файл только
через configured private API origin и fixed `/api/files/<opaque-filename>` path.
Returned URL никогда не используется напрямую; redirects запрещены. WAHA
groups create/admin и status posting условны и
по умолчанию не объявлены.

`personal_history_sync` выполняет manual bounded re-read newest pages, с
ограниченным `pageSize` и `maxPages`, без media download. Записи дедуплицируются
в собственной SQLite FTS index. Это не incremental event stream, не realtime и
не полный history import. Coverage включает source, time interval, watermark и
явную partial метку. В глобальном WAHA REST API не подтверждён full-text search;
MCP ищет только по собственному индексу.

### Official Business / Graph

Graph adapter закрепляет `graph.facebook.com` origin и конфигурируемую Graph
версию; текущий default v24.0. Он объявляет подтверждённые сообщения, templates,
flows, profile/account, media и analytics operations. CRUD/admin tools включаются
отдельным флагом; Business Groups tools отсутствуют.

Cloud API не предоставляет общий inbox для исторических incoming chats. Для
поддержанных webhook media IDs Graph adapter получает metadata по fixed media ID,
проверяет phone ID/MIME/size/SHA-256 и скачивает только на pinned
`lookaside.fbsbx.com` HTTPS host без redirects; сохранённый UUID отдаётся через
профильный MCP resource `whatsapp-media://<mediaId>`. Business
history index пополняется только Meta callback после настройки и проверки
webhook. Processor сверяет WABA ID и phone-number ID с конкретным instance, пишет
идемпотентные inbound events и хранит delivery state без регрессии на delayed
callbacks. Content из callback не превращается в инструкции. Из HTTP route наружу
доступны только Meta challenge и подписанный POST; Bearer gateway auth не заменяет
HMAC проверки.

## Identity, history и storage

Caller/account identity разрешается на gateway boundary или фиксируется local
stdio instance; tool args не могут подменить account. Каждая provider operation
проверяет account binding до запроса. Студенческий/клиентский provisioning должен
сопоставлять каждого пользователя с собственным service profile; текущая
архитектура не является произвольным shared-tenant router.

История и audit state лежат отдельно по профилям. FTS index ограничивает длину
поиска, page size и context. Message content, contact names, group data и provider
metadata относятся к недоверенному содержимому. Business `accepted` и message ID
не подтверждают delivered/read; delivery status приходит только из callback.

SQLite файлы проверяют приватный родительский каталог, запрещают symlink DB path,
включают WAL/FULL sync и права `0600`; media store имеет отдельный root `0700`,
файлы/metadata `0600`, no-follow access, UUID IDs, size/MIME allowlist и SHA-256
read-back. Runtime не шифрует SQLite файлы сам. Encryption-at-rest, retention и
production backup/recovery остаются host-level prerequisites и требуют отдельной
проверки до хранения реальных сообщений.

## Mutations и release identity

Каждая изменяющая операция публикуется как `*_prepare`; отдельный confirm tool
выполняет только зарегистрированный guarded operation. Durable audit сохраняет
caller, account, adapter, operation, digest нормализованных аргументов,
idempotency key, TTL, release revision и состояние, но не message payload.

Prepare не является human consent. Confirm требует отдельной явной owner
authorization по exact target/content, тот же caller/account/operation/argument
digest и тот же `WHATSAPP_RELEASE_REVISION`. Atomic single-use claim записывается
до upstream request. Переход release инвалидирует незаконченные approvals. После
restart `executing` становится `OUTCOME_UNKNOWN`; записи не повторяются
автоматически.

Проверка сохраняет выбранную цель и параметры; универсального upstream
compare-and-set контракта для всех provider edits/deletes нет. Не выдавать guard
за атомарную проверку provider state.

## Установка и update

Учебный HTTPS gateway маршрутизирует только точные `/mcp`, профильные `/media` и
отдельный Business webhook routes; MCP upstream auth — per-profile Bearer,
application сравнивает private token constant-time после снятия `Bearer `.
Прямой неавторизованный `/mcp` закрыт. Health показывает конфигурационный статус,
а не «connected».

GitHub CI проверяет build/tests и двигает только verified release reference.
Серверный updater работает от unprivileged identity, staging exact SHA, lock,
atomic symlink, readiness gate и rollback; state directories находятся вне
release. WAHA image pinned и обновляется отдельно. Подробные фактические host
пути, systemd/Podman/proxy setup и acceptance пока живут в
[`deployment/README.md`](../deployment/README.md).

## Открытые production gates

- Публичная GitHub публикация и deployment этого кода пока не подтверждены этим
  локальным snapshot.
- Проверить точное соединение публичных auth profiles с private service Bearer.
- Подтвердить owner-only link/recovery для QR, Meta app/webhook credentials,
  backup, retention и шифрование host state.
- Изолированная rootless WAHA container/network проверка, реальный webhook и
  downstream client roundtrip остаются deployment acceptance tests.
- Не поддерживать полный history import и Business groups без первичного
  доказательства provider capability.
