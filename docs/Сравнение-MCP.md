# Сравнение WhatsApp MCP и провайдеров

Срез первичных источников на 2026-10-06. Это исследование исходного кода, официальных README/API-спецификаций, лицензий и метаданных релизов. Ни один кандидат не подключался к личному аккаунту; QR не сканировался, сообщения не отправлялись. Заявленное в README покрытие не считается подтверждением стабильной работы каждой операции.

## Решение для первого выпуска

**Личный linked-device контур:** собственный ограниченный MCP-слой поверх WAHA Core `2026.9.2` с движком NOWEB. Использовать опубликованный upstream контейнер по закреплённому тегу/sha256, не включать образ, его исходники или сессии в GitHub-пакет. NOWEB выбран как движок без Chromium. Первичный образ для `linux/amd64`: `devlikeapro/waha:noweb-2026.9.2`, digest `sha256:0999fb384426222be591f3ffd15879f39b8940662df2f9f1d70d836a8315f659`; для `linux/arm64`: `devlikeapro/waha:noweb-arm-2026.9.2`, digest `sha256:d74d2062edb91e66e66271876ff5f35aff9c7d69e3bf2c0fe52ea7c4b43ea978`. Тег `2026.9.2-noweb` отсутствует. Реестр Docker Hub проверен 2026-10-06; см. [источник образов](Источники.md#pinned-metadata-snapshot).

Образ опубликован для отдельных архитектур, а не как единый multi-arch digest. Это важно для Compose: выбирать tag/digest по `linux/amd64` или `linux/arm64`, а не задавать один digest для обеих архитектур. Метаданные Hub указывают размер образа примерно 769 МБ для amd64 и 746 МБ для arm64; фактическое место после распаковки и расход памяти на учебном сервере не измерялись.

**Бизнес-контур:** отдельный адаптер к WhatsApp Business Platform Cloud API через Graph API. Для формы MCP можно использовать конечный список адаптерных tools; WBMCP служит актуальным source-level reference для типизированных Cloud API действий, но его bearer auth не заменяет действующий gateway/OAuth. Его Graph API default на исследованном commit — `v24.0`; версия остаётся конфигурацией и должна обновляться только после сверки официальной документации. WBMCP не принимает входящие webhooks сам: нужен отдельный проверяемый webhook receiver. Официальная Groups API существует, но её eligibility и доступность для нужного номера не подтверждены; обычные пользовательские группы нельзя считать доступными через этот API.

### Условия выбора

- WAHA Core с даты `2026.6.1` включает функции бывшего Plus и бесплатен по upstream документации. Для релиза `2026.9.2` используется именно Core образ.
- WAHA API и встроенный MCP защищаются API key. Внешний endpoint не должен напрямую публиковать WAHA: поставить принятый gateway перед нашим MCP, удостоверять субъект/tenant/account/scopes и передавать запрос только разрешённому account actor. Хранить upstream API key только на сервере.
- NOWEB store выключен по умолчанию. История включается при создании сессии через `config.noweb.store.enabled=true`; `fullSync` после pairing менять опасно: upstream предупреждает о потере истории. Источники не полностью согласованы: `NowebStoreConfig` DTO описывает `fullSync=false` неоднозначной фразой “only messages early than 90 days” и `fullSync=true` как все данные телефона; текущая NOWEB docs уточняет около 3 месяцев против около 1 года и максимум 100 000 сообщений на чат. Применять более консервативное ожидание и не обещать полный архив. WAHA также предупреждает не читать его SQLite store напрямую во время работы.
- В коде WAHA нет подтверждённого общего полнотекстового поиска по всем сообщениям. Встроенный API даёт список чатов и историю отдельного чата. Полнотекстовый поиск потребует собственного разрешённого индекса или будет `UNSUPPORTED`.
- WAHA имеет Streamable HTTP MCP на `/mcp`, но он использует `X-Api-Key`; для remote clients текущий проект строит собственный MCP endpoint поверх WAHA REST API и существующего gateway, а не отдаёт ученикам общий/сессионный ключ WAHA.
- NOWEB API покрывает нужные базовые операции по upstream source. Совместимость WhatsApp Web с будущими релизами не гарантирована. У WAHA несколько движков и поведение/event payload могут различаться; switching engine требует повторной проверки.

## Рекомендуемый первый capability set

До отдельной проверки тестовым аккаунтом объявлять только конечные операции, для которых WAHA `2026.9.2` имеет соответствующий REST endpoint. Все изменяющие функции — guarded и имеют явный preview/approval слой в собственном MCP. Сам факт, что WAHA endpoint существует, не подтверждает успешность конкретного сценария на целевом номере.

#### Инкрементальный локальный поиск и события

NOWEB по умолчанию не сохраняет сообщения; `enabled` выключен. После явной настройки SessionConfig GET chats/messages работают по ограниченному внутреннему SQLite store `store.sqlite3`, но upstream просит не открывать этот файл во время работы сессии. Поэтому проекту следует принимать только нужные события WAHA webhook и заносить нормализованные записи в отдельное собственное SQLite хранилище с устойчивым ключом `(account_id, chat_id, message_id)` и индексом/FTS. Это может дать поиск только по реально полученным и сохранённым событиям плюс разрешённый bounded backfill; это не создаёт обещания полного импорта прежней переписки. Event ingest должен выдерживать повторы и обновления/отзыв, сохранять audit/status, не выполнять операторские сообщения повторно. WAHA callbacks включают retry delivery, поэтому idempotency необходима.

Для сессии WAHA ожидаемый config shape:

```json
{
  "name": "account-scoped-session",
  "config": {
    "noweb": { "store": { "enabled": true, "fullSync": false } },
    "webhooks": [{
      "url": "https://<private-receiver>/waha/events",
      "events": ["session.status", "message", "message.any", "message.ack", "message.edited", "message.revoked"],
      "hmac": { "key": "<server-secret>" },
      "retries": { "policy": "linear", "delaySeconds": 2, "attempts": 15 }
    }]
  }
}
```

Это пример upstream contract, а не заданные на учебном сервере значения. Receiver должен хранить секрет отдельно для webhook route/account. WAHA подписывает JSON body; HMAC не включает timestamp/request-id headers. Receiver проверяет HMAC над неизменёнными raw bytes, сравнивает digest constant-time, отклоняет повторные/старые request IDs в ограниченном TTL и выполняет durable insert/upsert до `2xx`. Встроенный upstream retry делает dedupe обязательным.

| Flows/profile/commerce | Отдельные endpoints/permissions из Business Management/Flows APIs | Оставить как отдельные scopes и инструментальные группы; не включать в read/send минимальный профиль по умолчанию. |
| Groups | Meta предоставляет отдельную Groups API документацию | Groups API is present in Meta’s pinned v23 OpenAPI: create/list groups under a phone-number ID and group-ID routes for metadata, participants, invites, join requests and settings. Our initial release does not implement those routes because eligibility, scopes/permissions and access for the target WABA are unverified; Meta developer pages returned HTTP 429. Keep `UNSUPPORTED_PENDING_ELIGIBILITY`; do not claim support for ordinary consumer groups. |

Текущая Meta official Postman workspace описывает Cloud API и Business Management API раздельно. Она документирует messages endpoint, bearer user access token и необходимые для message API `whatsapp_business_messaging` permission и phone-number ID. WBMCP checked README конфигурирует Graph API `v24.0`; Meta API version надо проверять на момент релиза, не копировать прежний default бессрочно.

## Уровень уверенности и открытая проверка

**Подтверждено:** source files, controller paths и MCP transport WAHA; NOWEB store/fullSync guidance; published WAHA Core tags/digests/platforms в Docker Hub; GitHub commit/release/license metadata; Baileys npm dist-tags; основные source-level функции кандидатов; Meta official Postman documentation of Cloud API messaging, management collections and OAuth permission names.

**Не подтверждено:** реальная авторизация/QR на пользовательском номере; доставка, получение и receipt round-trip; history sync на сервере; Webhook resilience/signature implementation конкретного проекта; совместимость WAHA pin после последующих WhatsApp Web изменений; стоимость/CPU/RAM/latency; OAuth issuer/gateway и tenant mapping; права Business WABA и eligibility Groups API для целевого аккаунта; полный license/SBOM состав опубликованного WAHA image и каждой npm dependency; право перераспространения `delltrak/wamcp` несмотря на README MIT claim.

**Остаток:** до объявления каждой capability нужна отдельная contract/runtime проверка на тестовых аккаунтах; результат записывается по adapter + pinned version. Не включённая или недоказанная операция должна возвращать `UNSUPPORTED` либо быть выключена, а не изображать успех.
